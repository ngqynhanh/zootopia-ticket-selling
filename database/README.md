# Database

PostgreSQL 16 (14+ works). **The Flyway migrations are the source of truth:**

| File | Content |
|---|---|
| `backend/src/main/resources/db/migration/V1__init_schema.sql` | Core tables, constraints, indexes, `updated_at` triggers |
| `database/schema.sql` | Copy of all migrations in one file (for graders / manual setup), regenerated by the command below |
| `database/seed-data.sql` | Demo data, 100+ records (week 5) |
| `database/ER-diagram.md` | ER diagram (Mermaid) |

Flyway runs the migrations automatically when the backend starts. **Never edit a migration that is already on
`main` and has been run by a teammate**: add a new `V2__...sql`, `V3__...sql` instead.

Regenerate `schema.sql` after adding a migration (Git Bash, from the project root):

```bash
cat backend/src/main/resources/db/migration/V*.sql > database/schema.sql
```

## Schema at a glance (week 1)

**13 core tables + 2 junction tables:**

| Group | Tables |
|---|---|
| Users | `users` |
| Catalog | `ticket_types`, `combos` |
| Visit planning | `zones`, `activities` |
| Pricing | `promotions`, `group_policies` |
| Orders | `orders`, `order_items`, `group_bookings`, `verifications`, `payments`, `tickets` |
| Junction (many-to-many) | `combo_zones` (combo ↔ zone), `user_promotions` (user ↔ promotion) |

Supporting tables (refresh tokens, audit log, system settings, FAQ, notifications…) are added by new
migrations in the week their feature is built. See `docs/backend-roadmap.md`.

**Design notes**

- **Audit columns**: `created_at`, `updated_at`, `created_by`, `updated_by` on business tables.
- **Soft delete**: `is_active` + `deleted_at` on master data (users, ticket types, combos, zones, activities, promotions).
- **Business rules enforced by CHECK constraints**, for example:
  - a group has at least 10 visitors;
  - one guide serves at most 50 visitors;
  - `total_amount = subtotal - discount_amount`;
  - an order item is either a ticket type or a combo;
  - uploads are at most 5 MB and only jpg/png/webp/pdf.
- **Cascades**: deleting an order removes its items, tickets, payments and group details. Ticket types, combos and zones that orders still use can't be hard-deleted (`RESTRICT`), so they are soft-deleted.
- **Justified denormalization**: `order_items.unit_price` / `line_total` snapshot the price at purchase time, because catalog prices change later.
- **Indexes**: every foreign key (checked by `SchemaMigrationTest`), plus composite indexes for dashboards (`orders(status, created_at)`) and partial indexes for the scheduled jobs.
